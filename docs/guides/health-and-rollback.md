# 健康检查与回滚

更新命令成功不等于应用可用。健康检查用于验证更新结果；回滚是操作员确认后的独立操作，更新或探测失败不会自动回滚。

## 选择健康检查 {#health-checks}

当前普通更新流程中的更新后探测用于 Docker / Podman 单容器。分组目标不能因界面或适配器存在探针配置就视为已经接入完整流水线，详见[支持矩阵](../reference/support.md#runtimes)。

| 策略 | 适用情况 |
| --- | --- |
| 自动 | 优先使用运行时能力，作为首次配置的选择 |
| 运行时原生 | 容器已有 healthcheck；无 healthcheck 时的运行状态不等于业务就绪 |
| 手动 HTTP | 有明确的公网健康端点，需要检查状态码或响应内容 |
| 手动 TCP | 只需确认指定主机端口可连接，不验证应用协议 |
| 关闭 | 自行在外部验证服务，不以探测结果决定运行状态 |

HTTP 主机必须解析为公网地址；HTTP 端口允许 `80/8080`，HTTPS 允许 `443/8443/9443`。不跟随重定向。状态码未指定时按实现接受 200–399，但重定向响应仍会被拒绝；建议显式填写期望值，如 `200,204`。

默认自动检查使用等待期 15 秒、单次超时 10 秒、间隔 5 秒和探测窗口 180 秒。服务启动慢时调整等待期和窗口；探测窗口不包含前置等待期。失败策略可标记为失败或降级，均不会撤销已完成的更新。

## Kubernetes 拉取失败后的只读观察 {#image-pull}

对新提交的 Kubernetes Deployment，ReleaseTracker 会读取**本次目标** Pod 的等待原因。超时、临时连接中断或仓库 5xx 等确定为可恢复的拉取错误，在原就绪期限到达时**再次检查**；仍在重试才进入最多一小时的只读宽限期（无需重新部署，不增加部署尝试）。宽限期内每 30–120 秒复检，重启 ReleaseTracker 也不会重置期限。镜像不存在、鉴权失败、容器配置错误、CrashLoopBackOff、OOM 等确切故障直接结束；未知原因/权限不足不延长期限。Pod 错误原文可能含私有仓库 URL，持久化诊断仅保留归类后的原因码。

`RELEASETRACKER_READINESS_PULL_GRACE_SECONDS` 默认 1800 秒，可设为 0–3600 秒（例如 `3600` 为一小时），0 表示禁用；修改后重启才影响**新提交**的任务，已失败的旧任务不会被后台自动重放，可从任务页进行只读就绪复检。首次截止后重取证据，确认目标和执行器配置没有变化；Pod 模板指纹阻止外部改镜像被记作本次成功，而仅扩缩容不会因 generation 增加被误判为变更。新副本全部更新、就绪且可用后，即使 Kubernetes 保留旧 `ProgressDeadlineExceeded` 条件仍能结束观察。带 `@sha256:` 的不可变引用还核对所有目标副本 Pod 的实际 manifest digest；RBAC 不允许读取 Pod 或 ImageID 不可识别时不宣称成功。Tag 引用无法证明重新推送前后的镜像内容相同，建议对要求严格来源一致的服务选择 Digest 引用。

宽限期就绪后原任务、执行器和运行记录变为成功，并保留最初失败/延迟证据；如宽限期结束仍未就绪才按超时失败。手工复检也只读取状态，且只会修正仍为最新、未被替代的那次失败记录。对采用 `Recreate` 的 Deployment，镜像不可用可能造成服务中断，诊断面板会显示明显警告；请配合集群告警，不要把宽限期当作服务可用性保证。当前自动宽限仅适用于新提交的 Kubernetes Deployment，不适用于 StatefulSet、DaemonSet、Helm 或其他运行时。使用自动回滚前应由操作员评估副本和实际业务状态。

## 快照与保留 {#snapshots}

支持的破坏性更新会在变更前捕获重建所需配置，见[支持范围](../reference/support.md#runtimes)。快照不保证恢复容器 / Pod ID，也不包含持久卷、业务数据库或应用的数据迁移结果。

在执行器快照历史中选择目标快照并核对时间和镜像。锁定的快照不参与自动清理，也不能直接删除；使用中的快照受回滚占用保护。数量设置见[系统设置](../reference/settings.md)。

列表和详情 **API** 提供完整性状态：

| 状态 | 含义 |
| --- | --- |
| `verified` | 内容与保存的格式版本、SHA-256 和大小元数据一致 |
| `legacy_unverified` | 旧快照没有校验元数据，不等于已损坏，也不等于已验证 |
| `invalid` | 校验失败，不能用于恢复 |

新快照的规范化 JSON 最大为 **2 MiB**。SHA-256 是一致性校验，不是数字签名；它不能防御同时修改内容和摘要的数据库写入者。

## 回滚前预检（API） {#preview}

目前没有专用预检按钮。使用管理员 JWT 调用；`RT_BASE` 为实例外部地址（包含部署子路径），`EXECUTOR_ID` 和快照 ID 换成实际值：

```bash
curl --fail-with-body -X POST \
  "$RT_BASE/api/executors/$EXECUTOR_ID/rollback/preview" \
  -H "Authorization: Bearer $RT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"snapshot_id": 42}'
```

省略请求体时选择最新快照。检查 `snapshot_valid`、`integrity_status` 和 `validation_error`；请求成功本身不代表验证通过。预检不创建执行记录、不占用快照、不修改运行时。

预检只验证快照完整性与适配器兼容性，不模拟真实恢复，也不保证镜像仍可拉取、业务数据兼容或随后执行一定成功。

## 执行恢复 {#rollback}

1. 暂停可能触发新更新的自动策略，核对实际运行状态。
2. 确认应用支持降级，并备份受影响的应用数据。
3. 选择可用快照，完成预检后在执行器详情中手动回滚。
4. 查看回滚运行记录，并独立验证应用健康。

没有快照时不要反复请求回滚；按[支持矩阵](../reference/support.md#runtimes)使用对应平台的恢复机制。实例数据库恢复与执行器回滚不同，见[备份恢复](../operations/backup-and-upgrade.md#restore)。
