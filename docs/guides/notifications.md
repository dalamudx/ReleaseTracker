# Webhook 通知

当前仅提供 Webhook 通道，消息包含 Discord / Slack 兼容字段。通知用于接收事件，不会驱动或阻止执行器更新。

## 配置与测试 {#setup}

1. 在 **通知** 中添加 Webhook，填写接收地址并选择消息语言。
2. 选择需要接收的事件：新版本、重新发布、执行成功、执行失败或执行跳过。
3. 保存后使用 **测试发送**，同时确认接收方实际收到并正确显示消息。

重新发布指同一版本标签对应的上游内容发生变化。建议启用自动更新前至少测试失败事件的接收链路。

## 地址和安全要求 {#security}

- 仅允许公网 HTTP(S) 地址；HTTP 端口 `80/8080`，HTTPS 端口 `443/8443/9443`。
- 私有、回环、链路本地、容器网络和云元数据地址会被拒绝；不跟随重定向。
- Webhook URL 当前以明文存储在 SQLite 中，可能包含服务商令牌。保护数据库和备份，不要把完整 URL 粘贴到公开日志或问题报告。
- 不支持自定义 HTTP 请求头；需要专用鉴权格式的服务应在接收端适配。

## 投递行为 {#delivery}

新版本、重新发布、执行器结果和定时备份失败告警都先写入持久化队列，再由后台投递：服务重启或发送中断后会继续，失败按 30 秒、2 分钟、10 分钟、30 分钟退避重试，共 4 次后标记失败。发布投影和通知入队同事务提交，入队失败不会静默提交新投影并永久漏发。相同事件、版本和摘要会在本地队列去重，但不保证接收方严格只收到一次：发送成功后、确认投递前进程中断仍可能重发，接收方应自行实现幂等。通知器停用或取消订阅时，队列中的消息会被丢弃。测试消息成功也不能保证后续每次投递成功。

新版本通知按**渠道**判断：例如更新的预发布版本是追踪器的整体最新版本时，稳定渠道出现新版本仍会单独通知。定时备份失败使用“错误”事件，同一段连续失败只通知一次，成功一次后重新计数；告警只包含错误分类，不包含路径或密钥。

停用通知器会保留配置并停止发送。通知中的跳转链接依赖[BASE URL](../reference/settings.md)；发送失败按[通知排障](../reference/troubleshooting.md#notifications)检查。
